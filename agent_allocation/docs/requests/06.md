## Open

### R06-5 — extraction validity vs `tests/fixtures/adversarial/malformed_finals.json` (lead + 08)
The contract rule 06 implements (lead, M1): exactly one closed `<final>…</final>` → `VALID`; legality of the answer
inside is decided downstream. 08's fixture expects four such finals to be non-VALID at extraction:
`illegal option letter` (`<final>Z</final>`), `boolean hedge` (`<final>True or False</final>`),
`python prose instead of code`, `python with two fences`. Today those are `VALID` extractions that
(a) cast no vote (option/boolean identities are exactly 04's `text-normalize-v1`), (b) are graded `INVALID_OUTPUT` by
04 (`not_a_legal_option` / `not_an_explicit_boolean`) and 05 (unparseable program / `INVALID_CANDIDATE` public check),
and (c) count as state `I` in every 06 metric (known not correct, never an answer switch), so no result changes.
**Asked:** either 08 allows `valid` for those four cases and asserts the downstream `INVALID_OUTPUT` instead, or the
lead changes the rule to "form-validated extraction" (OPTION/BOOLEAN identity, PYTHON `ast.parse`) -- a small change
in `extraction/final.py` that also changes which priors 03 renders with the invalid-prior marker. 06 will not change
it without a decision.

### R06-6 — `live.select_and_seal` (lead)
1. Wrap agent 04's `math_equivalent` once per partition pass with `selection.plurality.memoized_equivalence`, so
   overlapping pools (`sample/k` prefixes, archives) get one verdict per ordered pair even when a call times out;
   `selection.partition.select_partition(paths, partition, seed=..., math_equivalent=...)` already does this.
2. A code checkpoint whose validly parsed candidate has no public check raises (select after public checks);
   `select_partition` reports such checkpoints as pending instead.
3. `seal_selections` may be called with every result on each pass: already sealed identical rows are skipped, only
   unsealed checkpoints form the next batch, a changed pool raises, and a changed re-run selection keeps the sealed
   row and emits `SealDriftWarning`. `PAUSED_CHECK_ERROR` rows are never sealed (`SealPendingWarning`): the
   checkpoint stays a blocker (no sealed row) until the public checker is repaired and a later pass seals the resumed
   selection -- this keeps "a checkpoint is sealed at most once" (07's reader invalidates a policy sealed twice) while
   a pause remains resumable. A pass whose results are all paused, with nothing sealed yet, raises `SealError`.

### R06-7 — seal chain semantics (lead + 07)
`previous_seal_sha256` is the `sha256` value recorded by batch `N-1` (`null` for batch 0). The supported reader is
`selection.seal.load_sealed_selections(paths, partition)`, which verifies digests, counts, the chain and contiguous
batches, and returns the effective row per policy. `analysis/load.py` and `tests/unit/analysis/synthrun.py` still use
the v1 `paths.selections(partition)` signature.

### R06-8 — nodes made terminal without a response (lead + 02, v2 R03-1)
`select_checkpoint` needs a `Candidate` for every pool member, so a context-limit node stored with `candidate: null`
would leave its checkpoints unselectable forever. 06 now reads a parsed record whose `candidate` is `null` as
`extraction.final.empty_candidate(node_id, task)` (parse `EMPTY`, no final) in `selection.partition.select_partition`
and `metrics.io.load_partition_records`. **Asked:** `live.select_and_seal` should do the same (or store
`extraction.final.terminal_without_response(spec, task)` as the candidate when the dispatcher makes such a node
terminal), so selections, grades (`INVALID_OUTPUT`) and metrics (state `I`) all see one record.
